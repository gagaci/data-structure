Why does this work?

The problem: given an array of integers and a target, return the indices of the two numbers that add up to it. Exactly one valid pair is guaranteed, and you can't use the same element twice.

The brute-force answer checks every pair — two nested loops, O(n²). The HashMap trick collapses that to a single pass by turning "does a partner exist?" into a constant-time question:

  • For each number nums[i], its partner must be complement = target − nums[i].
  • If we've already seen that complement, its index is sitting in the map — return both indices immediately.
  • If not, store nums[i] → i so a later element can find us as its complement.
Why check before storing? We look up the complement first, then insert the current value. That ordering is what stops an element from pairing with itself: when we're standing on index i, the map only holds indices 0…i−1, so any match we find is guaranteed to be a different element.

The default example uses nums = [2, 7, 11, 15], target = 9 — the answer [0, 1] is found early, on the second element. Toggle the Example button for nums = [3, 2, 4], target = 6: here 3 and 2 get stored first, and the match only fires on the last element, when 4's complement 2 is found waiting in the map, giving the answer [1, 2].
